# 注塑参数与尺寸偏差分析

核对保压、熔温和冷却时间与关键尺寸的层内关系，确定下一班怎么补测。

## 业务背景

岚川精密组件 · 成型工艺与量测室（模拟）。岚川精密有 12 台注塑机，早班给电器卡扣供应商交件。巡检员按样件号把机台成型日志与量测台记录关联成 CSV。现行做法是在 Excel 里画总体散点图，再按模具和机台手抄子表。工作台复算总体与各层的秩相关，并保留样件号、量测日和设备、树脂批次。工艺工程师据此拟定补测，质量值班长审批后交下一班执行。

- 不同模具和机台的工艺窗口叠在一起，总体趋势可能与单条生产线的方向相反。
- 机台记录的设定值和卡尺读数常重复，手抄排序容易漏掉并列秩次。
- 换料后首检件少，相关性和补样缺口容易在交班时混为一谈，回查还要翻两份台账。

### 双台账时间窗配对

机台成型日志与卡尺量测记录各有流水号，样件号可能对不上。配对页接收两本台账 CSV（各含流水号、样件号、量测日、模具、机台、树脂批次、记录时间及各自量测列），按以下口径处理：

- 按**量测日 × 模具 × 机台**分组，组内在**五分钟窗（默认 300 秒，可调 60–1800 秒）**内做一对一配对。
- 用最小费用最大流做字典序优化：**先最大化配对件数，再最小化两侧记录总时差**。
- 样件号一致且同组的记录直接**锚定**（确定性配对）；样件号对不上的才走时间窗。
- 对最优解中的每条配对逐一剔除后重算：剔除后无法保持同件数、同总时差的，才是**所有最优解都包含**的配对（入算相关）；存在并列最优替代配法的边整组转**待核对**，不参与相关计算。
- 样件号一致但时差超窗的锚定也转待核对，不自动入算。
- 同批**补录**按流水号合并迟到记录后对完整台账**整组重配**；每次配对存为不可变快照，已发分析可回查当时的配对。
- 结果页列出**本次入算配对（流水号溯源）**、**待核对配对**和**待核对记录**三张表。

相关接口：`GET /ledgers/spec`、`GET /ledgers/template/{side}`、`GET /ledgers/sample/{side}`、`POST /ledgers/preview`、`POST /ledgers`、`POST /ledgers/{id}/supplement`、`GET /ledgers/{id}`、`GET /ledgers/snapshots/{id}`、`POST /ledgers/snapshots/{id}/runs`。



## 演示日流程

1. 08:35 量测员在 IM-03 对模具 MJ-17 的卡扣取样，按 48.00 mm 外宽和 12.00 mm 台阶高记录有符号偏差。
2. 09:15 巡检员核对 IM-07 的 MJ-22 机台日志，检查 ABS-261118A/B 的标签与样件号是否一致。
3. 10:20 IM-11 用 MJ-31 加工完一轮，工艺员确认首末保压设定分别为 64 和 70 MPa。
4. 10:45 IM-05 的 MJ-44 新上模，仅有 4 条可配对的首检记录。
5. 11:05 巡检员上传 2026-11-18-卡扣首检与工艺联表.csv，核对 28 条样件来源。
6. 11:20 工艺员按模具 × 机台分层，用保压压力对卡扣外宽偏差复算，最低样本数设为 6。
7. 11:35 复核总体与三个可计算层的方向，切换树脂批次或熔体温度核查分层与常值影响。
8. 11:50 值班长核对补测清单和两端样件号，将同批两端抽样和首检缺口交下一班。

CSV 示例为 `2026-11-18-卡扣首检与工艺联表.csv`。批次记录保留 SHA-256 指纹，运行记录保存参数、结果和人工复核决定。更详细的边界条件和样例见 [TOPIC.md](TOPIC.md)。

## 口径与算法

- 输入是一件样件一行的机台日志与卡尺联表。偏差为实测尺寸减图纸名义值，保留正负和原始量测精度。
- 对总体和每个层分别给 X、Y 升序排秩，相同值取所占名次的均值。以 R、S 表示两列秩，ρ = Σ[(R−R̄)(S−S̄)] / √(Σ(R−R̄)² × Σ(S−S̄)²)。
- 最低样本数同时作用于总体和各层。样本不足或任一变量为常值时显示不可计算及原因。总体使用所有样件，包括未达门槛的层。
- 按未舍入的 ρ 比较方向，|ρ| ≤ 10⁻¹² 记为零。仅当至少两个可计算层都与总体反向时报告可计算层一致反转。其余反向逐层标记。
- 系数表、样件联表和补测清单可按层交叉核对。样件表展示此次选择的两列原值，以及各样件的总体秩、层内秩。
- 补测缺口按门槛减当前样本数计算。排查反转时建议在已批准的工艺窗内固定其余条件，在所选参数低、高两端各补测至少 3 件。
- 同一 CSV 和参数可复算。该分析用于确定补测与量具复核顺序。样本门槛是现场筛查口径，关联结果不能证明因果。

## 启动

需要 Docker 与 Compose v2。在项目目录执行下面的命令。

```sh
cp -n .env.example .env
docker compose config --quiet
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

前端 `http://127.0.0.1:18261`，FastAPI 文档 `http://127.0.0.1:19261/docs`，数据库 `127.0.0.1:17761`。

| 演示角色 | 账号 | 密码 | 权限 |
|---|---|---|---|
| 复核主管 | `admin` | `admin-demo-2611` | 导入、运行、结果复核、审计。含定时分发时可管理计划 |
| 分析员 | `analyst` | `analyst-demo-2611` | 导入、运行、浏览、导出 |
| 只读查看 | `viewer` | `viewer-demo-2611` | 浏览批次、运行和结果，可导出 |

切换账号请先退出。三个账号由确定性示例脚本创建，重复执行会保留现有账号和批次。

## 实现与本地开发

| 位置或服务 | 职责 |
|---|---|
| `frontend/src` | 原生 HTML/CSS/JS 模块，通过 Nginx ` /api/ ` 代理访问后端。改前端文件后执行 `docker compose up -d --build frontend` |
| `backend/src` | Python 3.11、FastAPI、SQLAlchemy。修改算法后执行 `docker compose up -d --build backend worker` |
| `backend/src/domain` | CSV 字段、可控样本、业务分析和参数元数据；`matching.py` 为双台账时间窗配对引擎，`snapshot_analysis.py` 把稳定配对接入秩相关分析 |
| `backend/tests` | 仅依赖标准库（服务/接口测试可使用隔离依赖）的单元与集成测试，`python -I tests/<file>.py` 运行 |
| `backend/migrations` | 表结构说明 |
| `worker` | 数据库任务领取、Redis 唤醒、计算、CSV 导出 |
| `db` / `redis` | MySQL 8.0 / Redis 7 |

`FRONTEND_PORT`、`BACKEND_PORT`、`DB_PORT` 设定本机端口。`DB_PASSWORD`、`JWT_SECRET` 为运行配置，`SEED_DEMO` 控制启动时生成演示账号和数据。`APP_SUBNET` 设定项目内网，可在地址冲突时调整。共 5 个服务，数据库、Redis 与共享导出使用各自的命名卷。`docker compose down` 停止并保留数据，`docker compose down -v` 同时清除本项目的卷。

前后端共有枚举 `Role`、`Status`、`Review`，分别定义在 `backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js`，用于鉴权、运行状态和复核展示。
